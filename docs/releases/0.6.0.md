# 0.6.0

This release adds a page that shows each image before and after, so you can see what shrinking does before anything changes. The command can also write WebP and AVIF copies of your images, compared at the same quality score as the PNG or JPEG it would write. The rule flags more of the images your code names, and stops flagging images it can't shrink without a visible difference. The commands no longer write over an image you excluded, one that is read-only, one that changed since the lint flagged it, or one that another folder's lint flagged.

It is also the first release under this name: the package was formerly oxlint-plugin-pngdeer, and follows its engine, which HeyDeer renamed from pngdeer to slimdeer. Coming from 0.5.0? Start with "Upgrading" below.

## See it before you shrink it

`npx oxlint-plugin-slimdeer --review [PATH...] [--open]` takes `--check`'s paths and options, except `--json`. It writes a preview of every image `--check` would list, and one page that compares each preview with its original, to `node_modules/.cache/slimdeer/review/index.html`. It changes no image and uploads nothing. In `example/`, with nothing cached yet:

```
$ npx oxlint-plugin-slimdeer --review
slimdeer: measuring 5 images not in the cache yet...
slimdeer: writing 5 previews...
slimdeer: 5 images could be 723 kB smaller (1.0 MB → 317 kB, 70% smaller). Images unchanged.
slimdeer: the page that compares each one before and after: file:///…/example/node_modules/.cache/slimdeer/review/index.html
slimdeer: open it in a browser, untick any image to keep as it is, and run the command it gives.
```

The page works from disk, with no server: drag a divider across each image, look at the pixels at 100% or 200%, untick what you want to keep, and copy the command for the rest. Each "after" is the file the command writes, byte for byte. [What the page does](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#review-images-before-and-after)

The page has a "Skip to the command" link, and its tally reads "could save", since nothing has changed yet. In a window 480 px tall or less, and on paper, the bar ends the page instead of covering an image. On paper, the command prints whole, without the Copy button. If the browser won't copy, the page selects the command and says under it to press Ctrl+C (⌘C on a Mac).

After a lint, `--review --flagged` writes the page for exactly the images the lint flagged, each at the target the lint measured it at, read from the lint's cache. The lint's summary offers it when it flagged two or more images:

```
slimdeer: to see the 4 flagged images before and after on one page first, run: npx oxlint-plugin-slimdeer --review --flagged
slimdeer: to shrink the 4 flagged images in place (lossy, so commit first), run: npx oxlint-plugin-slimdeer --flagged
```

`--check` offers `--review` the same way when it lists two or more images. With one image, both offer a preview as a new file with `-o` instead.

A review compresses each listed image once more, for its preview, and a second review reuses the previews. Without `--open`, it opens nothing and only prints the page's address, so a coding agent can run it and give you the address. When `--open` can't open a browser (xdg-open over SSH or in a container, say), it says so.

For coding agents, [the agent skill](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/skills/oxlint-plugin-slimdeer/SKILL.md) in this repository has an agent measure your images with `--check --json`, give you the review page's address, shrink only the images you approve, and, when you ask, write WebP or AVIF copies and list the code that still names the originals:

```bash
npx skills add lndgalante/oxlint-plugin-slimdeer
```

## WebP and AVIF

The command can write a WebP or AVIF copy of an image, next to it or to a file you name, at the quality score its PNG or JPEG shrink would have, so the two sizes compare at the same quality. Check and review first:

```bash
npx oxlint-plugin-slimdeer --check --format webp           # which images are worth it
npx oxlint-plugin-slimdeer --review --format webp          # see them before and after
npx oxlint-plugin-slimdeer --format webp public/hero.png   # write public/hero.webp
npx oxlint-plugin-slimdeer public/photo.jpg -o photo.avif  # write the copy you name
```

```
$ npx oxlint-plugin-slimdeer --format webp public/hero.png
public/hero.png → public/hero.webp: 509 kB → 92 kB (82% smaller, quality 87/100: looks the same side by side); shrunk as PNG at the same quality: 151 kB
slimdeer: public/hero.png is still there, and this line still names it; point it at hero.webp:
  src/App.jsx:10  <img src="/hero.png" alt="An arcade stick" />
  and 1 mention in Markdown: SOURCES.md:10
slimdeer: delete public/hero.png only once nothing uses it; other sites, emails and share previews may link to files in public/.
```

On this repository's example app, at the same quality scores: as WebP, three of the five images come out 32% smaller than shrinking them as PNG (793 kB now, 225 kB shrunk, 152 kB as WebP), while the photo comes out only 3% smaller than its JPEG shrink, so `--check --format webp` leaves it out. As AVIF, three come out 64% smaller than shrinking them (780 kB now, 247 kB shrunk, 89 kB as AVIF), but the diagram comes out 59% bigger than its PNG shrink, so it is left out. It depends on the image, so check before you convert.

- The original stays, and `--format` never writes over a file. The saving starts once your code names the copy: the command lists the lines that still name the original.
- With `--format`, a copy is written only where it is smaller than both the original and the PNG or JPEG shrink. With `-o`, it is written whenever it is smaller than the original, and the command says when the shrink would be smaller.
- Skip it where something already converts your images: the command says so when your package.json depends on `next`, `astro`, `gatsby`, `@nuxt/image` or `vite-imagetools`, since converting the source adds a second lossy pass there.
- Keep share images, app icons and images for email as PNG or JPEG; as AVIF, they can fail to show. In [a December 2024 test](https://joost.blog/use-avif-webp-share-images/), link previews on X, LinkedIn, Slack and iMessage didn't show AVIF (WebP showed on all 11 platforms tried), and Outlook for Windows [doesn't show AVIF either](https://www.caniemail.com/features/image-avif/). With `--format avif`, the command points out each image named like a share image or an icon.
- AVIF is slow: on the example app, `--check --format avif` took 66 seconds for five images, against 13 as WebP and 5 for the PNG and JPEG check, and one image alone often takes about a minute. `--check --format` and `--review --format` cache what they measure.

The lint rule suggests no format change: its fix keeps each image's name and format, so no code changes. [Everything about copies](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#write-images-as-webp-or-avif)

## What gets flagged

- CSS `url()` in JS: in inline styles, CSS strings, and styled-components or emotion templates. Only the path is underlined. A `url()` that runs into an expression is still not flagged.
- Every `srcSet` candidate with a `?query` or `#hash`, not only the first, each underlined where it is written.
- A root path like `/logo.png` is looked up in the `public/` and `static/` folders nearest the linted file first, so each app in an Nx workspace finds its own.
- React Native and Expo: in a project whose package.json depends on `react-native` or `expo`, a reference to `logo.png` also names `logo@2x.png`, `logo.ios.png`, `logo@2x.ios.png` and the other variants in the same folder, each warned at the same string.
- Gatsby: in a project that depends on `gatsby`, root paths are looked up in `static/`, and `public/`, the build output, is left out unless `publicDirs` includes `"public"`.
- Next.js: where `next/image` re-encodes the image for visitors, the warning adds "Here next/image re-encodes it for visitors, so shrinking it saves repository and build size." ([when](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#frameworks)). The image is still reported and shrunk as before; to skip a second lossy pass, add its folder to `exclude`.

## The quality floor

The automatic target no longer settles below quality 70, where the rule calls a result "visibly different": such an image is compressed again at target 70. If nothing reaches 70, the image isn't flagged, `--check` and `--review` don't list it, and the command leaves it as it is. An explicit target below 70 still allows such a result. The lint says how many images the floor turned down as it measures, and `--check` names them:

```
slimdeer: 1 image can't be made smaller without a visible difference (its best quality is below 70), so it isn't listed; to try it at a lower target, run: npx oxlint-plugin-slimdeer --check public/fade.png --target 60
```

On 148 images from the tanstack.com repository, the floor cut the list from 140 images that could save 74.4 MB in all to 136 images that could save 59.0 MB. Two 8 MB PNG headers account for 13.3 MB of the difference; the other two images dropped are `tanstack-start-solid-v2/header.png` (a 2.0 MB saving at quality 62) and `logo-color-100.png` (a 10 kB saving at quality 67). No "visibly different" result is left, where there were 7. A cold run, on a 16-core Mac that was running other work, took 90.6 s, 3.61 GB of memory at its peak and 718 s of CPU time, against 90.4 s, 3.78 GB and 661 s for 0.5.0. An image the floor turns down is compressed twice the first time: one 8 MB header took 56 s at the automatic target, and 31 s at `--target 70` alone.

To shrink one such image anyway, preview it at a lower target, then shrink it the same way. A `target` in the rule's options would apply to every image.

```bash
npx oxlint-plugin-slimdeer public/header.png --target 60 -o header.preview.png
npx oxlint-plugin-slimdeer public/header.png --target 60
```

## The check command

At a monorepo's root, `--check` now checks every package below it in one run, each image with its own package's cache and lock:

```
packages/docs/public/photo.jpg: could be 64% smaller (235 kB → 85 kB, quality 76/100: looks close, with differences you might spot side by side)
packages/docs/public/diagram.png: could be 75% smaller (248 kB → 63 kB, quality 90/100: looks identical)
packages/web/public/hero.png: could be 70% smaller (509 kB → 151 kB, quality 87/100: looks the same side by side)
slimdeer: checked 3 images in 2 packages; 3 measured, 0 cached, 0 skipped (already optimized or below 4.1 kB), 0 errors.
```

- `--exclude` matches a path from the image's package or from the folder the command runs in, so `packages/*/fixtures` works from the root.
- A lint now reads what `--check` measured for an image of another package (`../../shared/logo.png`), and `--review --flagged` reads it where the lint did, so neither measures it again.
- `--json` prints one JSON document on stdout and nothing else there, with the same exit codes. [Its fields](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#json)
- It names the images the quality floor turned down, images short of an explicit `--target` (with their best quality rounded down, so it never reads as reaching the target), Git LFS pointers (with `git lfs pull` as the fix), and files named like images that aren't PNGs or JPEGs (with the `--exclude` command that leaves them out). In a Gatsby project it leaves out `public/`, the build output, and says how to check it too.
- Sizes round the way a reader expects: 999,500 bytes read `1.0 MB` (0.5.0 printed `1000 kB`), and a percentage reads 100 only when nothing is left and 0 only when nothing is saved.

## Safer

- `exclude` also matches an image's real path: a linked folder, a linked file, and on macOS and Windows another letter case, where patterns now ignore case as `.gitignore` does there. Before, `--flagged` could rewrite such an image.
- `--flagged` uses only a list left by a lint in the same folder. A copied project, or a worktree that links another one's `node_modules`, gets "no list of flagged images here" instead of a rewrite of the other folder's images.
- `--flagged` and `--review --flagged` leave out an image whose bytes changed since the lint (a branch switch, a new export), say it "changed since the last lint here", and do the rest. `--flagged` compares each image again when its turn comes, so one that changes during a long run is left as it is too. Lint again to put it back on the list.
- When its folder, `node_modules/.cache/slimdeer/review`, is a link, `--review` stops and leaves the folder it leads to alone, since a review empties that folder of what it didn't write.
- An in-place shrink checks that the image didn't change while it was compressed. If it did, the image is left as it is, and the command exits `1`.
- `-o` refuses the image itself: the same path, another letter case on macOS or Windows, or a link to it. In 0.5.0 it wrote over the image.
- A read-only image is left as it is, with `permission denied` and exit `1`; the other images are still done.
- An image named twice in two spellings (`Logo.png` and `logo.png` on macOS and Windows, or through a link) is shrunk once, and `--check` counts it once.
- With `eslint --no-inline-config`, an image whose warning a disable comment turns off no longer goes into the summary's table or `--flagged`'s list.
- Control characters in file names show as U+FFFD in the warnings and in every line the plugin prints. A command it prints spells them as escapes (`photo$'\x09'copy.jpg` for a tab), so it runs as printed in bash, zsh and ksh. `--json` keeps the real names.

## Smaller things

- In GitHub Actions, the lint and `--check` write the job summary, with no option or permission: the flagged images, the quality legend, and the commands that review and shrink them, in blocks you can copy. They are `npx` commands, on Windows runners too, and `--check`'s name the folder to run them in when it ran below the checkout's root.
- On Windows, the commands the plugin prints write paths and `--exclude` patterns with `/`, which cmd.exe and PowerShell both take, and a name like `logo@2x.png` no longer needs the PowerShell form.
- A file name that starts with `=` is quoted in the commands the plugin prints. zsh, the default shell on macOS, reads an unquoted `=name` as a command's path and refused the whole line.
- A command-line lint, `--check`, `--review` and the shrink command use every core, 8 at most, where 0.5.0 left one free, so a 2-core CI runner measures two images at a time. An editor still leaves one core free.
- Off a terminal, progress says what is at stake: `slimdeer: measured N of M images, could save X so far...`. The smallest image goes first, so the first count lands sooner.
- A lock left by a run that died is taken over after a minute, whatever its process id. It used to take up to 15 minutes, and the wait was silent when a container reused the process id. The waiting line now reads `slimdeer: waiting for another lint measuring this project (if none is running, this one goes on within a minute)`.
- An engine that panics is replaced, so the images after it are still measured.
- Options that take a value accept `--name=value`, like `--target=80`. A usage mistake prints one line and a pointer to `--help`, not the whole usage. Piping the output into `head` no longer crashes the command.
- The summary's columns line up with wide characters (CJK) and decomposed accents.
- The cache no longer stores how long a measurement took, so a committed `cacheDir` gets the same files from every machine.
- Engine failures point to https://github.com/heydeer/slimdeer/issues.

## The engine: slimdeer 0.3.1

The engine in the package is slimdeer 0.3.1 (commit 38ce560), upstream's single-threaded build with AVIF output, which `--format avif` uses. AVIF is encoded with libaom, under the BSD-2-Clause license and the Alliance for Open Media Patent License 1.0, with parts of it under BSD-3-Clause and MIT. The engine writes the same PNG and JPEG files as 0.5.0's, so results in a committed cache folder carry over. We compared the two engines on 110 images, 440 results in all, and found no difference; test/engine-output.test.js checks a sample on every CI platform, and also pins one WebP and one AVIF file as this engine writes them. The package grows from 0.5.0's 0.70 MB download (2.3 MB unpacked) to 2.0 MB (5.9 MB unpacked), and each engine thread uses about 8 MB more memory. Two clean builds of the pinned source in GitHub Actions reproduced the shipped engine files byte for byte ([the run](https://github.com/lndgalante/oxlint-plugin-slimdeer/actions/runs/43168095056)); [engine/README.md](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/engine/README.md) has the recipe.

## Upgrading

Formerly oxlint-plugin-pngdeer, the package now has its engine's new name, and so do its command, rule, settings key and types: `npx oxlint-plugin-slimdeer`, `slimdeer/compressible-image`, `settings.slimdeer`, `SlimdeerPlugin` and `SlimdeerSettings`. Images shrunk by any version need nothing. Your lint config, scripts and CI take a few edits: [moving from the old name](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#moving-from-oxlint-plugin-pngdeer).

The cache format is unchanged, and the new engine writes the same PNG and JPEG files, so 0.5.0's results carry over in a committed cache folder. The local cache moved to `node_modules/.cache/slimdeer`, so the first lint on each machine measures every image again. In a `cacheDir`, only images whose automatic result scored below 70, or whose old entry is damaged or was edited by hand, are measured again, once. On tanstack.com's 148 images, with a cache folder 0.5.0 had filled, the first `--check` after upgrading measured again only the 7 whose 0.5.0 result was below 70.

- **A committed `cacheDir`:** the first lint or `--check --cache-dir` that measures writes new files for the automatic target. Commit them. 0.5.0's automatic-target files stay in the folder, unread; to drop them, delete the folder before filling it again.
- **`measure: "never"`:** until the cache is filled again, a lint doesn't check the images that have no result there, and says so once with the command that fills it. Without a `cacheDir`, run `npx oxlint-plugin-slimdeer --check` once. With one, run `npx oxlint-plugin-slimdeer --check --cache-dir PATH`, with PATH your `cacheDir`, then commit the folder. Add the rule's `--target` if it sets one.
- **`--flagged`:** run a lint once before it. 0.5.0's list doesn't say which folder its lint ran in, so it is ignored.
- **Images 0.5.0 flagged below quality 70:** they are compressed again at 70. Those that reach it are still flagged, with a smaller saving; those that don't are no longer flagged. On tanstack.com, 3 of those 7 were flagged again at quality 70 or 71, and 4 dropped out (see "The quality floor").
- **`--check` in CI:** it now checks nested packages too, so a step that gates on its exit code can fail where 0.5.0 passed (test fixtures, examples, vendored packages). To check only the root package, as 0.5.0 did, leave out every folder with a package.json of its own. Where those are all in `packages/` and `examples/`, that is `npx oxlint-plugin-slimdeer --check --exclude 'packages/*' --exclude 'examples/*'`; add any others, like `apps/*` or `docs`. `--check --json` gives each listed image's `package`.
- **`exclude` on macOS and Windows:** patterns now ignore letter case, so `public/originals` also leaves out `public/Originals`.
- **`-o`:** OUT's extension now says what to write: `.png` or `.apng` for a PNG and `.jpg` or `.jpeg` for a JPEG get the shrink, and `.webp` or `.avif` a copy. So `-o x.jpg` on a PNG, or an OUT with no extension, is a mistake in the arguments (exit 2) where 0.5.0 wrote the file.
- **Scripts that read the output:** the prefixes are `slimdeer:` and `oxlint-plugin-slimdeer:`, formerly `pngdeer:` and `oxlint-plugin-pngdeer:`. An image the command already shrank reads `already shrunk by this command; left as is`. The summary's leads, the preview and review lines, the progress and waiting lines, the "no list of flagged images" message and `--check`'s last lines changed too. A script should read `--check --json` instead of the text.

## Known limits

The engine's four known bugs are still there in slimdeer 0.3.1, and the plugin stays correct when they happen:

- A PNG with a smooth fade to transparent fails at explicit targets of 62 and up.
- Flat-color JPEGs fail to measure.
- PNG output drops the `eXIf` chunk; the plugin puts the orientation back.
- A grayscale PNG with a color profile comes out darker; the plugin skips these.

CI runs the whole suite on Linux, macOS and Windows with Node 20 to 26, and the new commands were also tried by hand on macOS. The PowerShell commands the review page gives are covered by unit tests. Gatsby, Expo and Nx support was tried on constructed projects, not on real installs.

With images at different targets and a cold cache, `--review --flagged` measures one target after another, which is slower. Right after a lint the cache is warm, so this doesn't show.

An image linked into another package is checked once, under the first path `--check` finds; a lint in the other package measures it once more, then reads its own cache.

A file name with bidi control characters (U+202E, say) can reorder how the review page shows the command. Copy takes the real names.

WebP and AVIF copies:

- AVIF is slow: one image alone often takes about a minute, and `--check --format avif` took 66 seconds for the example app's five images, against 13 as WebP. Writing a copy converts the image again, even after a check measured it.
- A PNG with a smooth fade to transparent can get no copy: at the automatic target its shrink stays below quality 70, so there is no quality to match, and at `--target 80`, the target the command then suggests, the shrink fails with the engine bug above (`slimdeer couldn't compress this image: unreachable`). The engine's WebP output fails on such an image at quality 70 too, as a test shows (`fade()` in test/helpers.js).
- Images this command already shrank, animated PNGs, PNGs turned by their eXIf data, Next.js `app/` metadata images, WebP over 16,383 pixels a side, AVIF over 24 megapixels, and AVIF in React Native projects get no copy; the command names each with its reason ([the list](https://github.com/lndgalante/oxlint-plugin-slimdeer/blob/main/docs/rules/compressible-image.md#images-left-out)).
- How Safari and Firefox show slimdeer's AVIF files hasn't been checked yet. Chrome showed them on the review page.
